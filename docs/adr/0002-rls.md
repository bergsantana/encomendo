# 0002 — Tenant isolation with Postgres row level security

- Status: accepted
- Date: 2026-11-24

## Context

All tenants share one database and one schema. A missing `WHERE tenant_id = …` in one query would leak one store's orders to another. Application checks alone are one bug away from a leak.

## Decision

Isolation is enforced three times: the JWT principal (or the store page subdomain), app-layer authorization, and Postgres RLS.

- Migrations run as `encomendo_owner`. The API connects as `encomendo_app`: `NOSUPERUSER NOBYPASSRLS`, not the owner, no DDL, grants table by table.
- Every tenant table has `ENABLE` and `FORCE ROW LEVEL SECURITY` and a policy on `current_setting('app.tenant_id', true)`.
- The TxManager sets `app.tenant_id` with `set_config(…, true)` inside each transaction, so a pooled connection never carries a tenant into the next request. With no tenant set, policies match no rows.
- Client accounts read their own orders across tenants through a second, `SELECT`-only policy on `app.client_account_id`. Supplier, cost and purchasing tables never get one.
- Local and CI roles come from `deploy/postgres/init.sql`; production roles come from the infrastructure.

## Consequences

- Every tenant table needs an RLS test suite (five cases, plus two for client policies).
- Every repository call must run inside `WithinTx`. Queries outside a transaction see nothing, which fails closed.
- Cross-tenant jobs need a separate role from `cmd/worker`, never from the API.
