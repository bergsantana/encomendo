# 0003 — JWT access tokens with rotating opaque refresh tokens

- Status: accepted
- Date: 2026-11-24

## Context

Staff log in on the web admin app and the Android app. Clients may log in on any store page and see orders from every store. Tokens must be cheap to verify on every request and revocable.

## Decision

- Access tokens: JWT signed with EdDSA (Ed25519), `kid` header for key rotation, 15 minutes. Claims `sub`, `tid`, `role`, `aud`, `jti`, `iat`, `exp`, `iss`. `aud` is `backoffice` or `client`.
- Verification pins the algorithm (rejects `none` and HS*), and checks `iss`, `aud`, `exp` and `nbf` with 30 s leeway.
- Refresh tokens: 32 random bytes, stored only as SHA-256, 30 days, rotated on every use. Reusing a spent refresh token revokes its whole family.
- Web keeps the access token in memory and the refresh token in an httpOnly cookie; Android keeps both in the Keystore.
- Clients log in with an email code or Google; they have no passwords. Staff passwords use argon2id.

## Consequences

- Logout and theft response work through refresh-family revocation plus a short Redis `jti` denylist.
- Implemented in milestone 2. See `docs/architecture.md` section 5.
